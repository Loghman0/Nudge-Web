# Discovery operations

The app uses 200 current authored/adapted questions and retains six historical starter definitions for existing answers and drafts. Starter edition 2 gives all six questions five contextual responses and literal observation mappings. This is an engineering seed, not a clinically validated instrument or a claim of human editorial review. Ordinary answers, selection, reflections and criterion suggestions make zero model calls. Written answers remain literal history; no automatic trait extraction. See [Question design review](QUESTION-DESIGN-2026-11-06.md) for the research and interpretation limits.

## Expanding the bank

1. `node scripts/discovery-pipeline.mjs briefs 200 .local/discovery-briefs.jsonl` creates taxonomy × context × angle × format briefs. The current seed's 55 domain/subdomain pairs produce 168,960 distinct work specifications; these are not guaranteed unique questions. The CLI refuses a requested count above the current taxonomy's capacity, with a hard ceiling of 250,000. Use small batches until engagement and quality have been measured.
2. Give a batch's synthetic briefs to the configured model in an operator-controlled offline job, using the bounded generation CLI below or a separate reviewed process. Never include user answers. Require JSON objects matching `src/lib/discovery/types.ts`. Keep provider/model/token/cost provenance alongside each result. Generation is disabled by default and never runs during a user's question session.
3. `node scripts/discovery-pipeline.mjs review candidate.json .local/discovery-review` checks shape, exact/token-overlap duplicates, tone and sensitive-content flags. Generated inference mappings are rejected. The report preserves rejected IDs and reasons; accepted candidates remain drafts. Embedding/model review can supplement these filters, never replace editor review.
4. Review the sample and every flagged item. Review each retained question's balance, cultural assumptions, standalone meaning, neutral responses and accessibility. In `review.json`, record `editorDecision` (`approve` or `reject`), `editor`, and a past UTC `reviewedAt` timestamp for each retained candidate. All inference rules need individual engineering/editor review. Sampling is for quality surveillance, not permission to skip retained-question or rule review.
5. `node scripts/discovery-pipeline.mjs approve .local/discovery-review .local/discovery-approved.json` produces an `approved_draft` artifact. It checks matching candidate and catalog hashes, decisions, reviewer declarations and dates; it refuses missing, changed, rejected or ambiguous records. The declaration is an audit record, not authentication of the editor or proof that a human performed the review. Candidate changes require a fresh review package. All output paths must be new, so rerunning cannot overwrite earlier decisions or approved artifacts.
6. Publish approved immutable versions through a reviewed catalog change and an additive SQL migration; deploy code and database together. The approval command does not publish or alter the live catalog or database. Never overwrite an answered version. Run catalog, database, privacy and browser tests. Roll back by retiring a version and stopping its selection; keep its original definition for existing answers.

For durable offline job packages, use `node --import ./tests/register.mjs scripts/discovery-jobs.mjs init <briefs.jsonl> <new-directory>` with at most 100 synthetic briefs. Then run `node --import ./tests/register.mjs scripts/discovery-jobs.mjs generate <directory> <limit>` with a limit of 1–100. The dispatcher sends only canonical synthetic prompts, records reservations before transport, uses the existing metered transport and configured prices, stops on accounting failure, and refuses to resend an uncertain interrupted attempt. Completed drafts export with `node --import ./tests/register.mjs scripts/discovery-jobs.mjs export <directory> <new-candidates.json>` and still require the review workflow above. It does not modify the published catalog or any personal database.

Generation requires explicit operator configuration in `.env.local`: `NUDGE_CATALOG_AI_ENABLED=true`, `NUDGE_CATALOG_AI_MODEL=lightning` or `gemma`, a positive `NUDGE_CATALOG_AI_DAILY_USD`, `NUDGE_CATALOG_AI_DAILY_REQUESTS` (1–1000), and `NUDGE_CATALOG_AI_MINUTE_REQUESTS` (1–60, no higher than the daily limit). The chosen model must be enabled in existing NVIDIA routing, have a matching entry in `NUDGE_AI_MODEL_PRICES_JSON`, and have its server-only NVIDIA key. Unknown prices refuse transport. A configured zero rate still consumes request quota. Leave the enabled flag false except for an intentional operator run.

`scripts/lib/catalog-ai-runner.mjs` uses a separate SQLite ledger at `.local/catalog-ai-ledger.sqlite`, with full synchronous writes and serialized transactions. Every package in this checkout shares its rate/cost limits. The ledger stores synthetic job IDs, transport metadata, token counts and configured cost; no keys, prompts or personal answers. Retain the database and its WAL together, and never delete or copy it to reset limits. This is a single-machine operator tool, not a distributed service or a vendor-wide spending limit across other checkouts/apps. Parallel or hosted workers need a shared operator ledger before use.

An unsettled reservation blocks further dispatch across packages, including after restart. Missing usage retains the reserved cost instead of becoming free. Interrupted `run.lock`, `dispatching` and `accounting_blocked` records require operator inspection of both the job journal and ledger; the CLI never clears them or retries uncertain requests automatically. Retain ambiguous charges until provider records resolve them. If a request was never sent, an operator may resolve that specific record after verifying the evidence; do not bulk reset the ledger. A failed request returns a nonzero CLI status and keeps its charged attempt. Rejected questions remain excluded from exports.

## Selection and evidence

The selector uses hard opt-outs, depth limits, recent-family suppression, coverage, explicit session mode and an 80/20 relevance/exploration mixture. Three answers or two skips prompt a pause. Topic choice overrides variety. Clock time only affects estimated effort; response speed is not an emotional diagnosis. Deeper and optional topics require explicit settings.

Profile evidence retains question ID/version and answer ID/revision. Contradictions remain mixed; they cannot produce a criterion suggestion. Confirmations are explicitly recorded. Suggestions expire after 180 days, offer at most three labels, show their source context, and never supply criterion weight, range, unit or option facts. Unknown/private settings receive no everyday-life transfer. A corrected answer invalidates dependent comparison caches through the existing privacy generation.

Accepted criterion suggestions are recomputed against the owner's current profile before saving. Private version-2 comparison snapshots retain criterion ID, suggestion ID, privacy generation and exact answer/question revisions. These links are excluded from public decision context and the comparison retry intent. Foreign, stale, suppressed, mixed or rejected sources are rejected again by SQL. Editing/deleting sources or rejecting their reflection withdraws the saved evidence; explicit comparison inputs and decisions remain available. A copied criterion is a new explicit input and must be reviewed again.

The public preview imports a generated six-question asset, six retained historical definitions and catalog-independent validators/reflection logic. It does not download the full 200-question bank. Existing drafts are pinned to their original edition; users can explicitly start the updated questions. Server parsing, insights and export resolve exact historical versions, while new selection uses the current catalog. Larger server catalogs will need indexed candidate retrieval before publication; the current selector works against the bounded seed bank.

## Privacy and retention

Guest previews use session storage. Choosing Save copies a draft to local storage with a 24-hour read-time expiry; it is only uploaded after authenticated review. Browsers cannot run expiry cleanup while closed, so expired bytes are removed on the next access. Clear after successful claim or discard. No answers are embedded in URLs or sent to an LLM.

Answers and revisions persist until owner deletion, memory reset or account deletion. Exclusion retains history but removes its profile contribution. All new private records are accessible only through owner-scoped RPCs. Export v6 includes answers, versions, revisions, exposures, feedback, settings and optional activity counts. Service-only retention purges request/exposure/activity records after 30 days through the daily pg_cron job when available, plus the existing authenticated check-in job. Verify the job after migration; do not claim a verified retention SLA from code alone.

Written answers and optional topics are disabled by default in both server configuration (`NUDGE_DISCOVERY_WRITTEN_READY=false`, `NUDGE_DISCOVERY_OPTIONAL_READY=false`) and the private database table `nudge_private.discovery_rollout` (`written_answers_ready=false`, `optional_topics_ready=false`). Each feature requires both its server flag and its database flag, followed by explicit user opt-in. Database RPCs enforce the database gate independently, so a direct client call cannot enable an unreviewed format. Only the database operator may update the private rollout table; anonymous, authenticated and service-role clients have no table privileges.

Ordinary choice, scale and ranking questions remain available. An operator can enable each gate only after reviewing that rollout. Do not prefix these gates with `NEXT_PUBLIC_` or treat a user preference as operator approval. Restart the app after changing server configuration. Turning either gate off stops new serving and saving for that format while preserving users' access to their existing history and deletion controls.

A narrow English phrase check pauses saving when text explicitly suggests immediate self-harm and offers a supportive message; it is not a clinical classifier, multilingual coverage, or monitoring service. It does not diagnose or route personal text to another service. Before enabling written answers, review representative language and ambiguity cases, confirm a supportive interruption without profile inference, and provide reviewed localized support guidance. Before enabling optional topics, review the question bank and opt-out flows. These reviews remain release work; an automated test pass does not satisfy them.

## Measurement and pilot

Consented authenticated events record event name/time without answers. Track daily answered users / daily active users, return cohorts, answer counts per voluntary session, skip/topic-change rates and Fits/Sometimes/Not-me feedback. These are usability measures, not proof of psychological accuracy.

Pre-signup conversion needs a separately consented anonymous funnel or a moderated pilot. It is intentionally not collected invisibly. In a pilot, record six-question completion, optional signup conversion, whether the reflection felt specific/useful, correction frequency, and whether a suggested criterion was retained. Compare against a decision-first baseline; review abandonment reasons and accessibility failures. Do not optimize time spent or answer volume alone. No pilot results have been measured yet.

## Remaining staged capabilities

Embedding-based deduplication, a distributed generation service, a staffed review console, multilingual safety evaluation and pilot-derived selector weights are not supplied by the initial deployment. The local operator dispatcher, review artifacts and versioned schema are the integration points. Do not advertise a hundred-thousand-question bank or validated personality model before those gates are met.
